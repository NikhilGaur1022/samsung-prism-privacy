User portal — localhost:5173

Subjects sign in with a one-time code, not a password. For this walkthrough the code is shown on screen — ask for it and the verify page displays it with a button that fills the boxes for you. Nothing to grep, no mail server needed.

It is on screen because EXPOSE_DEV_OTP=on is set in backend/.env. That flag is refused outright in a production or staging environment, and npm run preflight fails — not warns — if it is ever set in one, so it cannot travel with the code by accident. Turn it off and the codes go back to the server log: 

grep -A2 "dev OTP issued" .run/logs/api.out.log | tail -3

Existing subjects you can sign in as: nikhilgaur1022@gmail.com, rohit-b2ef5593@exportsel.test, meenakshi-8653d116@lifecycle.test. Or register a fresh one at /register — that page posts to a public self-registration route and shows you the code straight after, so you can go from stranger to signed-in subject without leaving the browser.

Flow 04 destroys data for real. The erasure path shreds encryption keys and deletes files. It is not a soft delete and there is no undo — that is the whole point of it. Run it against a test subject you don't mind losing, not against your own account.

01The pipeline can no longer lie

This is the headline fix. A session used to jump straight to ARCHIVED the moment tagging was committed — before redaction had run. Two sessions in your database were sitting ARCHIVED with unblurred faces in them. There is now a REDACTING state in between, and nothing reaches ARCHIVED until every single frame has a confirmed redacted derivative on disk.

as agent@prism.local
1
Start a session against an approved project and capture or upload three or four photos of people./new-session → /sessions/:id/photos
Expect

Photos upload one by one, each with a thumbnail. Face detection starts automatically.

Broken if

An upload returns a 500, or the page shows a raw error with a stack trace or a file path in it.

2
Tag the detected faces to the people in the session, then open review./sessions/:id/tagging → /sessions/:id/review
Expect

Every face is either tagged to a subject or explicitly left untagged. Review lists what will happen on finalize.

Broken if

Review lets you finalize while faces are still unreviewed, with no warning.

3
Finalize the session, then immediately look at its status./sessions
Expect

REDACTING, not ARCHIVED. This is the fix. The session is honest about the fact that blurring hasn't finished yet.

Broken if

It says ARCHIVED straight away. That is the old bug — the status is claiming redaction finished when it hasn't started.

4
Wait, then refresh. Redaction runs in the background./sessions
Expect

Within a minute or so it moves to ARCHIVED on its own, and only then does a handoff appear.

Broken if

It sits in REDACTING forever — that means the redaction worker isn't consuming jobs. Check flow 02.

5
Kill the redaction worker mid-run and finalize another session, then restart the worker.stop the worker: redaction process, then start it again
Expect

The session waits in REDACTING. When the worker comes back it picks the work up and finishes. Nothing is lost, nothing is silently archived.

This is the crash-safety change — redaction jobs are now queued durably instead of running inside the request.

Broken if

The session archives anyway, or the frames stay unredacted forever after the worker returns.

02The counter that used to say zero

Every screen counted "blocked frames" by listing the two failure states it knew about. Your database held 0 of those and 27 in a third state nobody listed — so the dashboards showed a clean project while none of its sessions could be handed off. The count is now written as its inverse: anything that isn't finished is blocked, including states that don't exist yet.

as dataadmin@prism.local, then dataowner@prism.local
1
Open the operator screen. This page is new — before it, "is redaction actually running" was unanswerable by anyone./queue-health
Expect

Four panels: Queues, Stalled jobs, Storage, Photos by redaction state. The numbers are live.

Broken if

The page 403s, or every number is zero while flow 01 clearly has work in progress.

2
While a session from flow 01 is still REDACTING, read the Photos by redaction state panel./queue-health
Expect

A non-zero count sitting in a pending state, dropping to zero as redaction completes.

Broken if

It reports zero outstanding while a session is visibly stuck. That is exactly the old bug, in a new place.

3
Sign in as the data owner and open the same project's processed data./processed-data
Expect

The blocked-frame count agrees with what queue health showed. Two screens, one number.

Broken if

The two disagree. They now share a single definition, so a disagreement means one of them is computing it locally again.

03Project export

Entirely new. Redacted derivatives only, owner's own project only, and every export writes an audit record — the audit trail replaces an approval workflow, so it isn't optional. The refusal in step 2 is the part most worth testing: an export from a session whose redaction stalled would otherwise ship the subject blurred out, silently, with no error.

as dataowner@prism.local
1
Find the export panel on a project with finished sessions./processed-data
Expect

A panel offering Build export, describing itself as redacted derivatives only.

Broken if

No panel, or it offers original unredacted images.

2
Try to build an export while a session is still REDACTING from flow 01./processed-data
Expect

A clear refusal naming how many frames are still processing and saying that exporting now would ship them blurred. Not a generic error.

Broken if

It builds anyway. Open the archive — if a face that should be visible is blurred out, this is the silent-corruption case the refusal exists to prevent.

3
Once everything is ARCHIVED, build it. Watch the status./processed-data
Expect

QUEUED → RUNNING → READY, with progress. The page stays usable — it builds in the background, not in the request.

Broken if

The browser hangs waiting, or it goes FAILED with no reason given.

4
Download it and open the zip. Windows Explorer is fine — it's a standard archive.Download button
Expect

Images open normally. manifest.json lists counts and names what was excluded. subjects.json is the identity map.

Broken if

The archive won't open, or the manifest says something was excluded without saying which.

5
Open subjects.json and search it for a real person's name or email address.the downloaded archive
Expect

No names, no emails — only opaque reference codes. Build a second export of the same project and the codes for the same person are different, so two archives can't be cross-referenced.

Broken if

Any real name or email appears anywhere in the archive, including inside image metadata.

6
Rename one of the exported JPEGs and move it to your desktop.anywhere on disk
Expect

It still carries its signed provenance stamp — the point is that a file separated from the archive can still be traced back and shown to be untampered.

Broken if

The stamp is gone. Verify with: node -e "import('./src/lib/imageMetadata.js').then(m=>m.readStamp('<path>').then(console.log))" from backend/.

04Erasure and the certificate

The compliance path. What changed here: erasure now sweeps the filesystem rather than walking database rows, because orphaned files — ones no row points at any more — were invisible to it. And the certificate now refuses to sign if a sweep still finds anything belonging to that person. It used to be willing to attest to a deletion that hadn't fully happened.

as a subject, then dataadmin@prism.local
1
Sign in to the user portal as a test subject and look at what's held on you.localhost:5173 → /my-data
Expect

A list of items with a total. Note the total — you'll check it again at the end. This page used to take up to three seconds; it should now come back in well under one.

Broken if

It takes several seconds, or the total contradicts the number of items listed.

2
Raise an erasure request./requests/new
Expect

The request is accepted and appears under My requests with a status and a due date.

Broken if

It submits into nowhere, or the request list stays empty.

3
Switch to the admin portal, open the request, and run discovery./dsar-queue → /dsar/:id
Expect

Every location holding that person's data, grouped by type — photos, face crops, voice attributions, text spans, consents. The voice attribution count is new; it used to count recordings, which is a different number.

Broken if

Discovery finds fewer items than /my-data showed the subject in step 1.

4
Execute the purge. This is the destructive one./dsar/:id
Expect

It completes and reports what it destroyed, including any loose files found by the filesystem sweep rather than by database lookup.

Broken if

It reports success while listing nothing, or errors halfway leaving the request stuck.

5
Issue the deletion certificate, then view it as the subject./dsar/:id → then localhost:5173 /requests/:id/certificate
Expect

A signed certificate the subject can see, listing what was destroyed and when.

Broken if

It signs while data is still on disk. If issuing refuses, that is the safety catch working — read the reason, it will name what it still found.

6
Go back to the export you built in flow 03, if that person was in it./processed-data
Expect

It has been revoked. An archive sitting on a server containing someone who exercised their right to erasure is the loophole this closes.

Broken if

It's still downloadable and still contains them.

05Security and UX sweep

Seven quick checks, two minutes each. Each one is a specific finding from the audit — a real thing that was wrong, not a hypothetical.

1
While signed in to the admin portal, type a URL that doesn't exist.localhost:5180/this-does-not-exist
Expect

A page saying it doesn't exist, naming the path, confirming you're still signed in, with the sidebar intact.

Broken if

You get the login form. That reads as "you've been logged out" and invites you to re-enter your password on a page you didn't expect — a phishing-shaped experience produced by our own routing.

2
Narrow the browser window below about 1000px wide.any admin page
Expect

A notice saying this width isn't supported. Phones are deliberately out of scope; the floor is 1024px.

Broken if

It just renders broken with content cut off.

3
Set the window to exactly 1024px and walk through several pages.any admin page
Expect

No horizontal scrollbar anywhere. All 54 role×page combinations were measured clean; this is your spot check.

Broken if

A page scrolls sideways — tell me which one and I'll trace it.

4
Put obvious junk where an ID belongs.localhost:5180/dsar/not-a-real-id
Expect

A clean rejection. Nothing is written to the audit ledger — junk used to be accepted and permanently recorded there, and those ledgers are append-only, so it could never be cleaned up.

Broken if

A 500, or a database error string reaches the screen.

5
As the data owner, copy another owner's project ID from the database and put it in the URL./processed-data or any project route
Expect

Refused. A data owner could previously read any project's details and assignment list, not just their own.

Broken if

You can see someone else's project.

6
Rename a text file to .jpg and upload it as a session photo./sessions/:id/photos
Expect

Rejected at the door with a clear message about file type. The contents are sniffed, not trusted from the extension.

Broken if

A 500 with an error from deep inside the image library — that means it got all the way to the decoder before anyone checked.

7
Sign out of the user portal, then go straight to the enrolment page.localhost:5173/enroll
Expect

Sent to sign in. Signed in but with nothing to enrol for, you get a real explanation and a way out — not a spinner that never resolves.

Broken if

A permanent "Loading…" with no way forward. That was a dead end with no escape.

06Video

New, and the largest single piece. There was no video screen in either portal before this. The backend routes and the Python worker both existed, and the worker’s own README said a human tags the clusters in the admin portal — but that human had nowhere to do it. Nothing called the analyser, nothing created the consent links that redaction reads, and DSAR discovery had no video query at all.

as agent@prism.local
1
Open an active session, find the Video panel, and add a short clip with people in it./sessions/:id
Expect

The clip uploads and shows a status. A few seconds of phone footage is plenty.

Broken if

No Video panel, or it says video is switched off — check the worker is running: docker compose --profile video up -d.

2
Run recognition, then open tagging and look at the person cards./sessions/:id/tagging
Expect

A small film badge on any card whose person is also in the clip, and a caption reading “Seen in 3 photos and 1 clip”. One person, one card, both media — you tag them once.

Someone who appears only in the clip gets their own card, pictured from the video.

Broken if

A card shows a broken image. That is the video-only person — they have no photo, and the card used to ask for one anyway, leaving someone untaggable and therefore blurred out of their own footage.

3
Tag one person, deliberately leave another untagged, then go to review and finalize./sessions/:id/tagging → review
Expect

Review tells you how many clips will be blurred before you press the button. The session moves to REDACTING.

Broken if

Review says nothing about clips. Blurring video is slower than blurring stills and is the most likely reason a session stays open afterwards.

4
Return to the session and play the blurred clip./sessions/:id → Video panel
Expect

The person you tagged is visible. Everyone else is blurred. This is the whole test. The panel states it is showing the blurred copy — the original is never played on an admin screen.

Broken if

Everyone is blurred, including the person you tagged. That means the consent link was not written, which is exactly the bug this work fixed — and it makes the footage useless.

Or the reverse: an untagged bystander is visible. That is a data-protection failure, not a cosmetic one. Stop and tell me.

5
While a clip is still processing, check the session status./sessions
Expect

REDACTING, and the Video panel explains that the session cannot be archived until every clip is blurred.

Broken if

ARCHIVED with a clip still processing. The gate counted photos only, so a clip could archive unblurred while an unblurred still of the same person was correctly held back.

6
Raise an erasure request for someone in the clip and run discovery./dsar/:id
Expect

The clip, its face attributions and its consent link all listed for destruction. If someone else is also in the clip it is marked for re-blurring rather than deletion — their consent to their own footage survives this erasure.

Broken if

Discovery lists no video. It found none at all before this work, so a person could be purged, certified, and told their data was destroyed with their face still in the footage.

07Backup and restore

A terminal flow rather than a UI one, and the item that guards the only failure here with no remedy at all. Worth running once yourself, so the procedure is not something only I have done.

1
Take a backup.cd backend && npm run backup
Expect

Rows, the sealed media tree, and a line reading fingerprints only — no key material written. The keys are deliberately absent: a backup holding both the locked media and the key that opens it is a plaintext copy of the whole system.

Broken if

It refuses — read the message. It refuses when a key is missing, because that backup restores into unopenable ciphertext and looks perfectly healthy until the day you need it.

2
Verify it.npm run verify:restore -- --backup ./backups/<stamp>
Expect

Keys match, sealed media intact, and real photos actually decrypt. Checks with nothing to look at report as --, never as passes — a verifier that only ever goes green on an empty system tells you nothing.

Broken if

Any line says FAIL. Each one names what to do about it.

3
Read the custody runbook and fill in the names.docs/KEY_CUSTODY.md §2
Expect

A table for owner, deputy and escalation — currently blank. This is the one thing in the whole piece of work that no script can do for you.

Broken if

It is still blank at go-live. One person holding the only copy of MEDIA_KEK is one resignation away from permanently destroying every photo in the system.

08What this walkthrough does not cover

Being explicit, so a clean run isn't mistaken for full coverage.
