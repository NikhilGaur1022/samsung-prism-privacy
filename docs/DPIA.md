# Data Protection Impact Assessment — Samsung PRISM

DPDP Act 2023 §10 (Significant Data Fiduciary obligations). This DPIA covers the consent-management and DSAR platform described in `docs/01_PRIVACY_DATAFLOW.md` and `docs/02_ROLE_PERMISSION_MATRIX.md`. Those two documents are the source of truth for architecture; this DPIA assesses the risk they describe and does not restate implementation detail beyond what's needed to justify a rating.

Status column legend carried over from doc 01: `BUILT` = works today · `PARTIAL` = exists but incomplete · `GAP` = must be built.

---

## 1. Scope

**Processing activity assessed:** supervised in-person photo and biometric (face) collection of volunteers for model-training datasets, from field capture through vault storage, derivative generation, and eventual erasure or export.

**In scope:**
- Collection Agent field capture sessions (consent → enrollment → photo capture)
- Automated face detection, clustering, and in-session tagging (Phase C, doc 01 §1)
- Bystander blur and PII text redaction (image-pii-worker, Phase D)
- Ingest to the golden vault store and derivative generation (Phase E)
- DSAR execution — access, correction, erasure (Phase F)
- The five admin tiers and one subject role defined in doc 02 §A

**Out of scope for this assessment:** the admin-portal frontend's UI/UX, non-photo consent flows (there are none today), and any future third-party Consent Manager integration (doc 01 §8, §6(6) — explicitly out of scope for this fiduciary).

**Data categories processed:** photographs of identifiable individuals, face embeddings (biometric data — a sensitive category under DPDP), subject PII (name, phone, email, date of birth), consent artifacts, and derived analytics/redacted datasets.

**Data principals:** photo subjects who are volunteers ("Data Principal" in doc 01 §0). Some volunteers may be minors — see risk register R8.

---

## 2. Lawful basis

**Consent-only posture.** No §7 legitimate use is claimed anywhere in this system. This is deliberate and stated in doc 01 §8 as "the simplest defensible stance": every processing act traces to a `ProjectConsent` row with a `consentId`, a `signatureHash`, and a frozen `policyVersion`. `project_consent_matrix` is the sole authority for what may be processed; intake boolean flags elsewhere in the schema are explicitly non-authoritative (schema comment, doc 01 §8 row §4).

Consequences of this posture for the DPIA:
- There is no fallback justification if consent is defective, withdrawn, or unproven. A gap in consent capture (e.g., the ConsentTemplate model — currently GAP per doc 01 §9 item 2) is therefore a lawful-basis gap, not merely a UX gap.
- Withdrawal (§6(4)) must stop *future* processing and trigger erasure of what isn't otherwise legally required (doc 01 §6.3). This is implemented at two gates today: `lib/consent.js` at intake and the re-check inside `finalizeSession()`.
- Because there is no legitimate-use fallback, the DSAR erasure path (§12) is not just a rights mechanism — it is the primary mechanism by which lawful basis is retracted. Its correctness (see R5, multi-subject erasure) is therefore a lawful-basis-integrity risk, not only a rights-fulfilment risk.

## 3. Necessity and proportionality

| Question | Assessment |
|---|---|
| Is biometric collection necessary for the stated purpose? | Yes — the purpose is supervised model-training data collection, which requires photographic and, for in-session matching, face-embedding data. There is no less-intrusive substitute for the tagging/clustering step given the operational model (agent-run field sessions). |
| Is the embedding retained longer than needed for matching? | Embeddings persist for the life of active consent (doc 01 §6.1: "until REVOKED, then 24h"), not indefinitely, and are never exposed through any read path (doc 01 §4 row "Face embedding (L5)": `○` for every role including super_admin — "no human path exists"). Proportionate. |
| Is bystander data minimised? | Yes by design — Phase D blurs every face not covered by a consent (`photo_subjects` mapping), and the redacted derivative, not the original, is what downstream roles and datasets ever see (doc 01 §4). |
| Is raw-original access minimised? | Yes — Collection Agent access to raw originals (L2) expires at session ARCHIVE (enforced server-side by `session.status` gating, not UI hiding). Data Owner never sees raw originals at all (doc 01 §4 note 2). Data Team Admin only inside a bound DSAR (`⚑`, doc 02 §C), and that path is now enforced end-to-end: `requireBreakGlass` (`backend/src/middleware/requireBreakGlass.js`) requires an open (`DISCOVERY`/`EXECUTING`) DSAR naming the specific subject on that specific object, a written justification of at least 20 characters, an `AccessEvent{breakGlass:true}` written *before* decrypt (`backend/src/lib/accessLog.js` — a log-write failure fails the read), and a same-request DPO notification (`DsarEvidence` row + audit entry). |
| Is the DPO's access proportionate to their role? | Yes — DPO governs process, not persons: no subject identity or raw media reaches DPO screens, which show pseudonymised refs (`SUB-a41f…`) only (doc 01 §4 note 1). |
| Is retention proportionate? | Mixed. L2 originals are 7 days post-archive (short, proportionate). L6 redacted derivatives default to 7 years (`Project.retention`), which is long but consistent with a training-dataset purpose and is per-project configurable, not a fixed floor. Backups (L11) at 35 days are the least controllable element — see R7. |
| Is this a Significant Data Fiduciary activity requiring full §10 rigor? | Yes — biometric processing at volume, with cross-project subject linkage, triggers §10 (DPIA + audit + India-based DPO), which is why this document exists. |

**Overall assessment:** the *design* is proportionate — least-privilege role model, per-project pseudonymisation, no embedding read path, short original-photo retention. The *implementation gap* is what currently makes several of these proportionality claims aspirational rather than actual (see §5, risk register, and the GAP markers below).

## 4. Risk register

Likelihood and Impact are rated Low / Medium / High against the population of volunteers processed by this platform. "Mitigation implemented" reflects **only what is BUILT today** per doc 01; where the mitigation is itself a GAP, that is stated, not smoothed over.

| # | Risk | Likelihood | Impact | Mitigation implemented | Residual risk |
|---|---|---|---|---|---|
| R1 | Unmasked PII (e.g., Aadhaar-like text in frame) reaches the vault or a dataset export | Low | High | **Resolved this cycle — now BUILT, fail-closed.** `detectPiiRegions` (`backend/src/modules/sessions/session.service.js`) no longer returns `[]` on a worker error; it throws `PiiUnavailableError`, which is a distinct type from "worker confirmed no PII," so the caller can never confuse the two. On that error the photo is parked `piiStatus=DEFERRED`, `redactedPath=null`, and every serving route (`readRedactedPhoto`, the per-person view, the principal's own §11 view) refuses a `DEFERRED` photo with a 409 rather than falling back to the raw original — there is no code path left that reaches for `storagePath` on a photo whose masking is unconfirmed. A retry is enqueued (`enqueueRedaction`) for `worker:redaction` to clear. | **Low, with an availability caveat, not a confidentiality one.** Nothing can leak unmasked PII any more — a photo either has a confirmed-clean/masked derivative or it is served to nobody, including its own subject. The residual is that clearing a `DEFERRED` photo depends on `worker:redaction` actually running against a working Redis (≥6.2) — on this dev machine's Redis 5.0.14 that retry does not work (see `docs/HANDOFF.md` §6.1), so a deferred photo can stay deferred indefinitely until Redis is upgraded. That is a stuck-availability failure, not an unmasked-PII failure. |
| R2 | Bystander (non-consenting individual) captured and identifiable in a stored photo | Medium | Medium | Bystander blur runs at Phase D against `photo_subjects` consent mapping before any derivative is servable; raw originals are access-restricted (L2, agent-only pre-archive) and time-limited (7-day retention). | Low-Medium. Redaction is BUILT and applied to every session, but relies on face-detection recall — a bystander whose face is not detected (poor angle, occlusion) is not blurred. No secondary human QA step exists in the pipeline today. |
| R3 | Insider (admin-tier user) accesses raw media outside operational need | Low | High | **Resolved this cycle — now BUILT and enforced, not just specified.** `AccessEvent` exists (`backend/src/lib/accessLog.js`) and `recordAccess` **throws** on a write failure — a media read whose log entry didn't persist is refused, not served ("no log, no read"). `logAccess` middleware writes it before any decrypt on the ordinary read paths; `requireBreakGlass` (`backend/src/middleware/requireBreakGlass.js`) enforces all four parts of the doc 02 §C protocol server-side: role restricted to `dataAdmin`/`super_admin`, an open (`DISCOVERY`/`EXECUTING`) `DsarRequest` naming the specific subject on the specific object (membership check, not equality, since a photo can hold several subjects), a justification ≥20 characters, and a same-request DPO notification via a `DsarEvidence` row plus an audit entry. Denied attempts also write an `AccessEvent{action:'DENIED'}` (best-effort, so a denial can't itself become an outage). | Low-Medium. The control is enforced, not policy-only, and every use is logged and DPO-visible in the same request. Residual risk is narrower now: no automated check on justification *quality* (any ≥20-character string passes), and detection still depends on the DPO or an auditor actually reviewing the `DsarEvidence`/`AccessEvent` feed rather than a hard real-time block on suspicious patterns. |
| R4 | Face embedding exfiltration | Low | High | No decrypt-to-response path exists for embeddings at any tier, including super_admin (doc 01 §4: "no human path exists"); embeddings are AES-256-GCM encrypted at rest (`embeddingCrypto.js`, BUILT) and read only inside the matcher process, zeroed after use. | Low. This is one of the strongest controls in the system — the absence of a route is a stronger guarantee than an access-controlled route. Residual risk is limited to a compromised matcher process itself or a KEK compromise (see R7). |
| R5 | Multi-subject erasure destroys a co-appearing subject's lawful data | Low | High | **Resolved this cycle — now BUILT.** The purge executor (`backend/src/modules/dsar/purge.service.js`) operates on the `PhotoSubject` LINK, never the photo: `PHASE_ORDER` runs `LINK → L6 → L2` (load-bearing, not cosmetic — `L6` needs the original, so it must run before `L2` deletes it). The `L6` handler rebuilds the redacted derivative via `rebuildRedactedForRemaining` when any link remains, blurring the erasing subject as a permanent bystander. The `L2` handler counts remaining `PhotoSubject` links on the photo and returns `SKIPPED` — keeping the original — while any link remains; it only shreds the original once the *last* link is gone. This exact bug (`L2` shredding unconditionally) was found and fixed this session — see `docs/HANDOFF.md` §3 item 3 — and is now covered by `backend/tests/e2e/dsar-erasure.test.js` (erasure on a photo holding two people). | Low. The invariant is enforced in code and tested, not merely specified. Residual risk is the ordinary one for any executor: a location can end `FAILED` and leave a `PurgeJob` `PARTIAL` rather than `COMPLETED` (e.g. a storage read error), in which case `issueCertificate` explicitly refuses to certify anything less than 100% complete — so an incomplete erasure is visible as "not yet certified," never silently reported as done. |
| R6 | Key compromise (KEK or per-project/per-subject DEK) | Low | High | Envelope scheme derives per-project/per-subject/per-path DEKs from a master KEK (`backend/src/lib/keyring.js`); `keyId` embedded in the blob header makes KEK rotation non-breaking, with lazy re-encrypt on read. **Correction to this document's earlier text:** the envelope scheme is now BUILT in `backend/src/lib/storage.js` for L2/L4/L6/L7/L8 (every `writeFile`/`readFile` call goes through it), not GAP as previously stated here — only L5 embedding encryption was ever a separate mechanism (`embeddingCrypto.js`). | Medium, for an operational reason rather than a missing-mechanism one: encryption is **opt-in via `MEDIA_KEK`** and is currently OFF in this environment (`MEDIA_KEK` unset — `docs/HANDOFF.md` §6.3), so today's corpus is plaintext on disk. `storage.js` refuses to boot with encryption off when `NODE_ENV=production`, so this cannot ship to production unset — but until `MEDIA_KEK` is set, the migration script (`scripts/migrate-media-encrypt.js`) is run against the existing corpus, and `MEDIA_REQUIRE_SEALED=on` is turned on (see `docs/DEPLOY.md` §4), a storage-layer compromise exposes raw photo blobs directly. |
| R7 | Backup residue survives erasure | **High (by construction)** | Medium | Crypto-shredding: destroying a subject's per-subject DEK renders all L4/L5 biometric artifacts for that principal unrecoverable in O(1), *even inside backups that cannot be rewritten* (doc 01 §3.2, §6.2; executed by the purge `SUBJECT_KEY` phase, always last in `PHASE_ORDER`). | **This residual risk is not fully mitigated and must not be described as resolved.** Crypto-shredding only covers subject-keyed artifacts (L4, and the embedding rows). Project/path-keyed artifacts (L2/L6/L7 originals and redacted derivatives — keyed by session/project path, per `scopeForPath` in `storage.js`, not by subject) are **not** subject-keyed, so a subject's erased photo can persist in a backup snapshot in recoverable form until that backup cycles out. This is now bounded by whatever backup retention window the production environment actually uses (this DPIA previously cited 35 days; confirm the current figure against the deployed backup policy before quoting it externally) — an accepted, time-boxed residual exposure, not a solved problem. Additionally, until `MEDIA_KEK` is set in production (see R6), L2/L6/L7 backups are plaintext-readable outright, independent of any key. |
| R8 | Minors enrolling without guardian consent | Medium | High | None built. Doc 01 §8 row §9 states plainly: guardian/verifiable-parental-consent flow is **GAP**. `Subject.dateOfBirth` exists as a field but nothing gates enrollment on it. | **High and open.** Volunteers may be minors; DPDP §9 requires no tracking/targeted-ads on children's data and verifiable parental consent for processing. Today the platform has no age gate and no guardian-consent flow at all — a minor can complete the identical adult consent flow. Not addressed this session. |
| R9 | Audit trail insufficient as forensic evidence of *what* happened during an incident | Medium | Medium | `AuditLog.payloadHash = HMAC-SHA256(...)` with `prevHash` chaining gives tamper-evidence (doc 01 §3.3, BUILT). For the one class of mutation where this matters most — erasure — there is now a purpose-built answer: `backend/src/modules/dsar/certificate.service.js` issues an Ed25519-signed `DeletionCertificate` per completed purge, carrying a canonical-JSON payload with a pre-deletion `hashBefore` for every location and a stable pseudonym (never the subject's real id) — this is the "DSAR certificates need their own signed record table" design intent from doc 01 §6.1, now BUILT rather than pending. | Medium, narrower than before. The general-purpose `AuditLog` remains hash-only by design — the chain is per `(entityType, entityId)`, not global, and payload plaintext is never stored, so it proves nothing was silently altered but does not reconstruct *what* a mutation was. That limitation is now fully compensated for erasures specifically (the `DeletionCertificate` carries real content, signed) but still applies to every other mutation type — session edits, consent changes, tagging decisions. Do not expect the general audit chain to answer "what exactly changed" for anything other than a certified erasure. |
| R11 | **Imported data has no lawful basis** — an admin ingests a person's pre-existing photographs with no capture-time consent behind them | **High (by construction)** | High | **Recorded, not prevented.** `backend/src/modules/import/import.service.js` resolves a live `ProjectConsent` at ingest time if the admin named a project; if there is none, or it is `REVOKED`, the item is written with `PhotoSubject.consentId = NULL` and `SubjectDataItem.meta.lawfulBasis = 'IMPORT_UNVERIFIED'` (plus `meta.consentGap` naming why). The alternative — manufacturing a `ProjectConsent` row to satisfy a NOT NULL — was rejected outright: that is forging the exact record this system exists to keep honest. The gap is surfaced in discovery, in the item grid (`byOrigin.IMPORT`, a per-row "Unverified" pill), and in the import UI before the first file is chosen. Import into an `ERASED` subject is a hard 409. | **High and open by design.** Under the consent-only posture of §2 there is no §7 fallback, so an `IMPORT_UNVERIFIED` item has *no lawful basis at all* — it is held, findable, erasable and honestly labelled, but its retention is not justified by this document. Two operational controls bound it: the route is `dataAdmin`/`super_admin` only, and every batch names an admin and a written provenance note. **Before any production import run, a lawful basis must be established out of band** (a signed consent captured through the ordinary flow, or a documented §7 ground added to §2 of this DPIA). A large volume of `IMPORT_UNVERIFIED` items is a compliance finding waiting to be written, and the count is deliberately visible on the item grid so it cannot accumulate unnoticed. |
| R12 | An imported frame carries an unblurred bystander | Medium | Medium | **Partial, and stated on every item.** Imported photos go through the same `enqueueRedaction` path as captured ones, so PII *text* (Aadhaar/PAN/plate) is masked by image-pii-worker with the same fail-closed `DEFERRED` behaviour as R1. Face blurring, however, is driven by `FaceDetection` rows, which are produced by the recognition worker, which is driven by a session — an import has none, so there are no boxes to blur and `meta.faceDetection = 'NOT_RUN'` records that on every imported item. | **Medium and open.** An imported group photograph is stored with every face visible, and its "redacted" derivative differs from the original only in PII text. Nothing serves it below `dataAdmin`, and it cannot enter a dataset export (the vault path is fed by session handoff, not by import), so the exposure is bounded to the DSAR surface and the subject's own §11 package — where the co-appearing bystander's face is not blurred. Closing this means running detection on import, which is a recognition-worker change and not an import-service one; it was deliberately not attempted in this phase rather than half-built. |
| R10 | ConsentTemplate / notice content is not itemised, plain-language, or multilingual as §5 requires | Medium | Medium | A join-flow renders consent text pre-signature today. | Medium-High. Doc 01 §8 marks the ConsentTemplate model itself as GAP — versioning and structured notice rendering do not exist yet, so §5 itemised-notice compliance rests on whatever static text is currently in the join flow, not a governed, versioned template. |

## 5. Explicit statement of unmitigated / partially mitigated residual risks

Updated this cycle. Three items that were open at the previous revision are now built and enforced in code (marked resolved below, not deleted, so the change is visible). The remainder are named here without softening, per the instruction that unresolved risk must be stated plainly:

1. **R7 — backup residue.** Crypto-shredding of the per-subject DEK makes subject-keyed artifacts (L4, embedding rows) unrecoverable in backups, but project/path-keyed photo data (L2/L6/L7) is not covered by that mechanism and can survive in a backup after a subject-driven erasure until that backup cycles out. This is an accepted, time-boxed residual, not a fully closed risk — and it is presently *worse* than "encrypted but time-boxed," because `MEDIA_KEK` is unset in this environment (R6), so L2/L6/L7 backups are plaintext-readable outright, independent of any key, until the KEK is set and the encryption backlog is swept per `docs/DEPLOY.md` §4.
2. **Resolved — R1, PII-worker failure.** Previously: "An outage of image-pii-worker currently allows unmasked PII text to reach the vault." This is no longer true. `detectPiiRegions` now throws `PiiUnavailableError` on any worker failure instead of returning `[]`, and the photo is parked `piiStatus=DEFERRED` with no serving path (including to the photo's own subject) until a redaction retry clears it. The residual is availability, not confidentiality — see R1 above.
3. **Resolved — R5, multi-subject erasure.** Previously: "the DSAR purge executor that would enforce it does not exist yet." It now exists (`backend/src/modules/dsar/purge.service.js`), operates on the `PhotoSubject` link rather than the photo, and is covered by `backend/tests/e2e/dsar-erasure.test.js`. The specific bug this section used to warn about — a code path doing `photo.delete()` unconditionally on erasure — was found in the executor's `L2` handler and fixed this session (`docs/HANDOFF.md` §3 item 3).
4. **R8 — no minor-consent gate exists.** Unchanged, still open. This is a straightforward §9 compliance gap with no compensating control today. Not addressed this session.
5. **R6 — media-at-rest encryption is BUILT but opt-in and currently OFF.** Correction to the previous revision of this document, which described the envelope scheme itself as GAP for L2/L4/L6/L7/L8 — it is not; `backend/src/lib/storage.js` implements it for all of those locations. What remains true is that `MEDIA_KEK` is unset in this environment, so the mechanism is inactive and the corpus is plaintext. `storage.js` refuses to boot in this state when `NODE_ENV=production`, so this cannot reach production silently — but it must still be actively set, followed by `scripts/migrate-media-encrypt.js` and `MEDIA_REQUIRE_SEALED=on`, per `docs/DEPLOY.md` §4, before the guarantee is real for this deployment.
6. **R11 — imported data may have no lawful basis, and the system records that rather than solving it.** New this cycle, with the import pipeline. Under the consent-only posture of §2 there is no legitimate-use fallback, so an item flagged `IMPORT_UNVERIFIED` is data this platform holds and cannot presently justify holding. It is fully discoverable, fully erasable, and labelled as such everywhere it appears — but labelling is not a lawful basis. **No production import run should proceed until either a consent is captured through the ordinary flow for the subject in question, or §2 is amended to claim a specific §7 ground and this document is re-signed.** The count of `IMPORT_UNVERIFIED` items is on the item grid precisely so this cannot quietly become the normal state.
7. **R12 — imported photographs are not face-blurred.** New this cycle. PII text masking runs; bystander face blurring does not, because there is no face detection on the import path. Bounded to the DSAR surface and the subject's own package, and recorded per item as `meta.faceDetection = 'NOT_RUN'`. Open.
8. **Resolved — R3, `AccessEvent` logging.** Previously: "does not exist yet." It now does (`backend/src/lib/accessLog.js`), is written before every decrypt, fails the read on a write failure, and the full break-glass protocol in doc 02 §C is enforced server-side by `requireBreakGlass` rather than existing only as written policy.
